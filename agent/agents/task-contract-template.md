# Task contract template

役割間で仕事を引き継ぐための記録です。既存 task に記録する場合は task ID を再利用します。新規作成時は、現環境で案内された `@@@task` の構文と notes の操作を使ってください。以下の項目名は記録用であり、Intent の API schema ではありません。

未取得は「未取得」、該当しない項目は理由付きで「対象外」と記します。記載した状態と環境側の状態値は区別し、利用できない値を API に送信しません。

## 依頼と担当

| 項目 | 記入内容 |
|---|---|
| task ID | 作成済みなら実際の ID。未作成なら未発行 |
| 親 task ID | 元の依頼または依存する task |
| 期待する結果 | 誰の何が、どう変わればよいか |
| 受け入れ条件 | 成否を確かめられる条件を番号付きで記載 |
| 対象範囲 | 編集、調査、確認する対象 |
| 対象外 | 今回は扱わない対象と操作 |
| 入力資料と証拠 | 読む資料、ログ、URL、成果物の保存先 |
| 担当スペシャリスト | 正式名と specialist ID。例：✋️Builder / `builder` |
| 担当 agent ID | 起動済みの実行主体の実際の ID。specialist ID と混同しない |
| 完了責任者 | ✋️Delivery Lead / `delivery-lead` と、実際の agent ID |
| 依存関係 | 待つ task、先に必要な成果、並行できる作業 |
| 許可された操作 | 読み取り、編集、実行、commit、push、外部更新などの実際の許可範囲 |
| 承認条件 | 承認済みの根拠、未承認の操作、人間の判断が必要な条件 |
| workspace | 作業ディレクトリの絶対パスと worktree の所有者 |
| 現在の SHA | 対象ブランチと完全な SHA。未コミット変更の有無も記載 |

## 検証

| 条件 ID | 入力と手順 | 期待値 | 実際値 | 対象 SHA・実行 ID | 証拠 | 判定 |
|---|---|---|---|---|---|---|
| AC-1 | 実施する操作 | 成功条件 | 実測結果または未実施 | 対象を識別する値 | ログや成果物の参照 | 合格・不合格・未確認 |

確認していない条件を合格にしません。変更前の再現、変更後の確認、統合後の確認は、それぞれの SHA と実行条件を残します。✋️Reviewer は specialist ID・実際の agent ID と判定根拠を記録します。

## 状態と再開

| 項目 | 記入内容 |
|---|---|
| 記録上の状態 | 待機、実行、レビュー、合格、不合格、阻害のいずれか |
| 環境側の状態 | 現環境が対応する状態値と、記録上の状態との対応 |
| 最終更新日時 | タイムゾーンを含む日時 |
| 実行情報 | 実在するセッション、プロセス、実行 ID。未確認なら未確認 |
| 再試行 | 問題、初回の結果、再試行回数、各回の仮説と結果 |
| 阻害要因 | 進められない理由、試したこと、必要な判断 |
| 再開条件 | 何が揃えば、誰が、どこから再開するか |
| 次の担当と作業 | 引き継ぐ相手の正式名・specialist ID・実際の agent ID と、具体的な次の一手 |

同じ問題への再試行は初回を除いて原則2回までです。並列書き込みは最大2 Worker、作業用 worktree は原則3までとし、ファイルごとの編集担当を重ねません。

## 提出結果

達成した結果を受け入れ条件と対応付けて記します。成果物、最終 SHA、workspace、検証結果、✋️Reviewer の判定を添えます。未完了と未確認の事項を残し、実装、検証、統合、マージ、デプロイのどこまで終わったかを分けて書いてください。

独立実行、通知、停止、再開、永続化などが利用できない場合は、その制約と実際に使った代替手順を記録します。プロンプトに指示があることだけで、機能が動作したと報告しません。
