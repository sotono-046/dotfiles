# Intent 用の階層型エージェントプロンプト

人間との対話を続けながら、開発現場が修正と再計画を行い、証拠付きの完了まで進めるための6役です。各ファイルは単独で Intent の Custom Specialist に貼り付けられます。他のファイルの自動読み込みは前提にしていません。

元資料は [ChatGPT の会話](https://chatgpt.com/c/6ad11056-0600-83e8-9e64-9d0d0a7b09b5) です。2026年10月16日に取得した本文から、対話と実行の分離、現場内の復旧、完了責任をプロンプトにしています。元資料で主張されていた Pi や各 CLI の現行 API は、このパッケージでは確認していません。添付画像の内容も取得本文には含まれていません。

## 登録する役割

| 正式名 | specialist ID | プロンプトファイル | 担当 |
|---|---|---|---|
| 🐓Product Steward | `product-steward` | `01-product-steward.md` | 目的、優先順位、人間との対話 |
| ✋️Delivery Lead | `delivery-lead` | `02-delivery-lead.md` | 分解、委任、復旧、独立レビュー、統合 |
| ✋️Explorer | `explorer` | `03-explorer.md` | 事実の調査、再現、原因の絞り込み |
| ✋️Architect | `architect` | `04-architect.md` | 設計、変更範囲、実装順序 |
| ✋️Builder | `builder` | `05-builder.md` | 実装、自己検証、局所的な修正 |
| ✋️Reviewer | `reviewer` | `06-reviewer.md` | 独立した確認と合否判定 |

`task-contract-template.md` は役割間の引き継ぎに使う記録のひな型です。Intent へ登録する7人目の Specialist ではありません。

## 使い始める手順

1. 登録済みの6役は、上表の正式名と specialist ID で識別します。プロンプトを更新するときは対応するファイル全体を指示欄へ貼り付け、ユーザーが設定した名前・実行環境・モデルを維持します。
2. 実環境で使えるツール、notes、`@@@task` の操作、状態値を確認します。実行権限と承認条件は、環境側と個々の task で設定します。
3. 🐓Product Steward に依頼し、成果と受け入れ条件を整理します。実行を担当する ✋️Delivery Lead へ引き継ぎます。
4. ✋️Delivery Lead が ✋️Builder と ✋️Reviewer を使って進めます。✋️Explorer と ✋️Architect は必要な場合だけ起動します。
5. 最初の一件で、実装中にも対話できるか、局所的な失敗から復旧するか、独立レビューと証拠付きの完了報告まで進むかを確認します。

6役を定義しても、6プロセスを常時起動する必要はありません。各役は登録済みの実行環境とモデルで起動し、独自のモデル指定で上書きしません。モデル変更を比較する場合はユーザーの選択を受けて、同じ受け入れ条件を使います。

## 委任時の指定

Intent v2.212.1 の同梱ソースで、specialist ID は設定ファイル名から `.md` を除いた値であることを確認しています。表示名やモデルを変えても、ファイル名を変えなければ ID は変わりません。

`workspace_api` が提供されている場合、現行の呼び出し例は次のとおりです。`taskNoteId` は実在する task note の ID に置き換え、呼び出し前に現環境のツール説明を確認します。

```js
ws.agent.delegate({ taskNoteId: "<実在するtask note ID>", specialist: "delivery-lead" })
ws.agent.create("調査担当", "<具体的な依頼>", { specialist: "explorer" })
```

`ws.agent.listSpecialists()` で現在の ID・正式名・既定モデルを確認し、`specialist` を省略せず上表の ID を指定します。登録済み設定を使うため、`model`・`provider`・`reasoningEffort`・`behaviorPrompt` の独自指定は加えません。`specialistId` という引数や表示名は、この指定の代わりに使いません。起動後の連絡に使う agent ID は、specialist ID と別に記録します。

同じ ID の定義はプロジェクト、個人用、組み込みの順に優先されます。読み込まれた正式名と指示が一致しない場合や未登録の場合は、別の役割で代用せず設定の不一致を報告します。組み込みの Coordinator、Developer、Implementor、PR Reviewer、Verifier は、この6役とは別のスペシャリストです。

## 運用の既定値

並列に書き込む Worker は最大2、作業用 worktree は原則3までです。同じファイルの担当を重ねません。読み取り専用の調査では不要な worktree を作りません。同じ問題への再試行は初回を除いて原則2回までとし、その後は仮説、担当、設計を見直します。

既存の承認を引き継ぎ、同じ許可を繰り返し求めない指示にしています。要求変更や承認不足の操作では、実行可能な範囲を進めたうえで必要な判断だけを人間へ返します。マージ、デプロイ、削除は指定された承認条件に従います。

pstack は、実際に提供され、作業に適用できるスキルだけを使います。スキルがあると仮定した固定コマンドは含めていません。`tdd` は明示的な要求がある場合だけ使います。

## プロンプトで保証しないこと

このパッケージは行動指示です。権限の強制、プロセスの常駐、独立した非同期実行、通知、途中指示、停止、再開、状態の永続化は実装しません。利用可能な機能を実環境で確認し、不足する場合は制約を報告するよう各役へ指示しています。

notes に記録があることと、実行環境が再起動後に自動回収できることも別です。登録後の実動作、Dropbox のクラウド同期、実際の開発品質は、保存されたプロンプトだけでは確認できません。

## 試行時の記録

人間が再指示した回数、目的を説明し直した回数、現場が自律的に復旧できた件数、完了までの時間と費用、開発中の対話継続、成果物の品質を記録します。モデルや課題の違いも併記し、役割分担だけの効果と断定しません。
