# PR変更ページの視覚確認

PRの変更が反映された実ページをローカルで開けるようにし、対象ページへの箇条書きリンクを一時HTMLにまとめる。コードを読む目的は、表示対象と起動方法の特定に絞る。コードレビュー、修正、PRへの投稿、公開・マージは別の依頼がある場合に行う。

## 対象PRとページを確かめる

- 指定されたPR、現在のリポジトリ、直近の会話から対象を決める。候補が複数あり一意に決まらない場合だけ確認する。
- PR URL、base/headのcommit SHA、起動するcheckoutとそのHEAD、未コミット変更を確認する。PR差分はbaseとheadの共通祖先から読み、ローカルの作業差分と混ぜない。
- 変更ファイルをroute・画面名へ対応づける。ページ本体のほか、共有component、CSS、画像、原稿・CMS seedも見る。共有変更は実際に影響するrouteを絞り、対応を確定できないものは未確定として残す。変更のないページを習慣で一覧に加えない。
- 「ページ名 / route / 表示が変わる理由」を短く整理し、同じrouteはまとめる。動的routeには表示できる既存のサンプルを使う。対象ページがない差分なら、その根拠を伝え、空のプレビューは作らない。

## PRの内容を表示する

起動には、利用可能なら [local-preview-start](../local-preview-start/SKILL.md) を使う。README、package scripts、設定から実際の起動方法を選ぶ。

- PR headを表示できる既存checkoutと正常なサーバーがあれば再利用する。dirtyな作業場所を切り替えたり、既存差分を戻したりしない。必要なら一時checkoutまたは分離したworktreeを使う。
- 一時コピーや `git archive` を使う場合は、元のcommitとコピー範囲を記録する。PR headと別のcommitを使うなら、PRの表示変更をどう反映したかを確認し、残る差を明記する。古いソースに新しい原稿を載せただけの画面を、PR headそのものとして扱わない。
- 実アプリのlayout、CSS、画像、原稿を使う。リンク集が簡易であっても、リンク先のページを独自のHTMLで描き直さない。CMSやDBから原稿を読む場合は、PRの原稿がローカル画面に届いているか確認する。必要な環境が使えず一部しか再現できない場合は、その範囲を示す。
- 既存サーバーの起動元とportを確認し、別の作業のprocessを停止しない。ローカル用hostと空きportで起動し、実際のURLを取得する。応答後もサーバーが動き続けるterminalまたはprocessを使う。

## 一時HTMLにリンクをまとめる

既存ファイルを上書きしない一時ディレクトリに `index.html` を作る。指定されたtempがあればそこを使い、なければ `mktemp -d` などで作る。成果物をアプリの正式なページやGit管理対象へ追加しない。

一覧は見出しと `<ul><li><a>` を基本にする。PRの識別情報と表示元を短く添え、ページ名から対象のローカルURLへ移動できるようにする。必要なら各リンクに変更点を一言添える。カード、iframe、詳細なレビュー表は求められた場合に追加する。

- hrefには実際のhost・port・base pathを含める。一覧を別portで配信する場合も、リンクがアプリのrouteへ向くようにする。
- タイトルや変更理由をHTMLへ入れるときはescapeする。認証情報をURLやHTMLに埋め込まない。
- 一覧をHTTPで開けるようにする。静的サーバーが必要なら一時ディレクトリだけを公開し、リポジトリ全体を配信しない。静的HTMLの配信とアプリの起動を混同しない。

## リンク先を開いて確かめる

見た目の確認には、利用可能なら [ui-screenshot](../ui-screenshot/SKILL.md) を参照する。

- 一覧をブラウザで開き、対象リンクから各ページへ移動する。HTTP応答に加えて、目的の画面とPRの変更箇所が表示されることを確認する。SPAの404相当画面、ログイン画面、古いCMS原稿をHTTP 200だけで見逃さない。
- 変更に関係するviewportと表示状態で撮影し、文字・画像の欠落、重なり、余白、スクロールを目視確認する。レスポンシブ変更は影響する幅で見る。変更前との比較が必要なら、同じ条件でbase側も撮る。
- browserや撮影機能が使えない場合も、リンク集の作成とHTTP確認まで進める。未確認の画面を具体的に伝え、見た目を確認済みとは報告しない。
- PRの見た目に問題が見つかったら、ページと症状を報告する。修正依頼がなければPRのコードを変更しない。確認用リンクやプレビュー起動の不具合は、この作業内で直す。

## 引き渡し

最初にリンク一覧のURLを返す。対象ページ、PR headと表示元、確認できた範囲と制約、一時ファイルの場所、サーバーを維持しているterminalまたはprocessを簡潔に添える。必要なら停止方法も示す。リンク集の作成完了と、各ページの表示確認結果を分けて伝える。

このスキルの元になった操作と、記録内で確認できなかった点は [references/recorded-workflow.md](references/recorded-workflow.md) にある。由来を確認するときだけ読む。実行時にComputer Historyや元のメモリファイルを読み直す必要はない。
