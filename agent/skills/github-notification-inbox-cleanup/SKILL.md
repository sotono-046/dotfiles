# GitHub通知の受信トレイ整理

受信トレイのGitHub通知をアーカイブし、メールをGmailに残したまま整理する。通常は個人用・仕事用の両方を確認し、アカウント・期間・リポジトリなどの指定があれば優先する。

## 対象と操作経路

- 実行時のGmailコネクタの接続一覧とプロフィールで、個人用・仕事用を識別する。`link_id`、メールID、ブラウザのアカウント番号を過去の記録から流用しない。一意に決まらないアカウントだけ質問する。
- Gmailコネクタを優先し、利用できなければログイン済みGmailのブラウザを使う。接続できないアカウントは未確認として残し、もう一方の作業は続ける。
- アーカイブを依頼され、対象が確定していれば追加の承認を求めず進める。件数確認・手順説明・スキル作成だけの依頼では、メールを変更しない。

## 通知を選ぶ

各アカウントで、次の条件を出発点に検索する。これは記録から復元した検索式ではなく、今回の整理用に定義した条件である。

```text
in:inbox from:notifications@github.com
```

- 送信元の実アドレスと件名などのメタデータで、Issue・PR・Discussion・CIなどの通知か確認する。表示名や本文中の「GitHub」だけで選ばない。認証・セキュリティ・請求などのアカウント連絡は対象に含めない。
- 未読・既読、期間、スターの有無で勝手に限定しない。除外条件を指定された場合は反映する。
- 別の通知送信元やGitHub Enterpriseが確認できた場合だけ、その通知に合う条件を追加する。`from:github.com`や単なる`github`検索の結果を、そのまま一括処理しない。
- 検索結果の次ページがあれば最後まで取得し、アカウント別に対象IDを重複なく集める。推定件数や最初のページだけで全件と判断しない。対象0件は正常な結果であり、検索範囲を無理に広げない。

## まとめてアーカイブする

検索のページ取得を終えてから変更する。変更しながら同じページトークンをたどると、検索結果の移動で取りこぼす可能性がある。

- メッセージ単位のラベル変更を使える場合は、確認したmessage IDから`INBOX`だけを除去する。現在の`gmail_batch_modify_email`では`message_ids`と`remove_labels: ["INBOX"]`を指定する。アカウントごとに実行し、tool schemaの上限に合わせて分割する。
- `gmail_archive_emails`はthread IDを受け取り、スレッド内の全メッセージから`INBOX`を除去する。スレッド単位の操作を使う場合は、対象外の受信メールが混在していないか確認する。混在していればメッセージ単位の操作を選ぶ。
- ブラウザでは、現在のアカウントと検索条件を確認してから対象を選択し、「アーカイブ」を実行する。ページ内の全選択と検索結果全体の全選択を区別し、複数ページを取りこぼさない。会話表示ではスレッド内の対象外メールにも注意する。
- 削除、既読化、ミュート、購読解除、GitHub側の通知設定変更、自動フィルタ作成を追加しない。0件なら変更toolを呼ばない。
- 結果が不明な操作は再検索して状態を確かめ、まだ受信トレイにある対象だけ1回再試行する。同じ対象で再び失敗する、または接続・権限のエラーが続く場合は、そのアカウントの処理を止めて未処理を報告する。

## 残件を確認して報告する

各アカウントで同じ検索条件を新しく実行し、残件を確認する。完了表示やtoolの成功応答だけで残件0としない。残件があれば対象と失敗理由を確認し、上の再試行範囲で処理する。新着通知は追加で1回まで処理し、最終検索で残った件数を報告する。新着を追い続けない。

アカウント別に、実際に処理できた件数・残件・未確認や失敗を短く伝える。メッセージ数とスレッド数を混同せず、スレッド単位なら「件」など単位を明記する。片方が未確認なら「両方とも残り0」と報告しない。

例: 「個人用は23通をアーカイブ、仕事用は対象0通でした。再検索で、両方の対象通知が受信トレイに残っていないことを確認しました。」数値はその実行結果に置き換える。アーカイブ後の新しい返信で受信トレイに戻ることはあり、将来の通知まで止めたと説明しない。

過去の操作や検索条件の根拠が必要なときは、[記録と仕様の根拠](references/workflow-evidence.md)を読む。
