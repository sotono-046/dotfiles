# サブエージェントチーム運用（司令塔・参謀・実装役）

メインセッションを司令塔とし、**名前付き・バックグラウンド常駐のサブエージェント**として参謀と実装役を召喚する。参謀・実装役とは `SendMessage` で文脈を保持したまま何往復も対話する。使い捨ての一発 fan-out（task-orchestration）とは異なり、**同じ相手に追加質問・前提変更の共有・レビュー往復ができる**のが本質。

## トリガー条件

- 「チーム編成して」「参謀を立てて」「参謀と相談」「サブエージェントチームで」
- 技術選定・セキュリティ設計・仕様レビューなど、調査と実装を並走させたい中〜大規模タスク
- 実装中に何度も「裏どり付きの相談相手」が必要になる作業

区別軸は「別プロセス（pane）か、同一セッション内サブエージェントか」。ユーザーが Herdr / pane を明示した場合、または `HERDR_ENV=1` の環境で Herdr 経由の編成が求められた場合は `herdr` スキルを使う（Herdr は Claude Code 自身も pane で統括できる）。それ以外の「チーム編成」はこのスキル。

## 1. 役割定義

| 役割 | 実体 | 責務 |
| --- | --- | --- |
| 司令塔 | メインセッション（自分） | タスク分解、指示出し、成果物の統合・レビュー、実測・最終判断、ユーザーへの報告 |
| 参謀 | 常駐サブエージェント（`model: fable` 推奨、読み取り中心） | 技術選定、公式ドキュメントでの裏どり、設計レビュー、devil's advocate |
| 実装役 | 常駐サブエージェント（1〜N体） | 割り当てられたファイル集合の実装・修正・コミット |

原則: **司令塔は手を動かしすぎない**。司令塔が直接やるのは (a) 軽量な実測・検証、(b) 成果物レビュー、(c) 統合判断。まとまった調査は参謀へ、まとまった実装は実装役へ。

## 2. 召喚（Agent ツール）

各メンバーは `Agent` ツールで **`name` を付けて** `run_in_background: true` で起動する。名前が SendMessage の宛先になる。

```
Agent:
  name: "strategist"            # 宛先になる。役割がわかる名前にする
  subagent_type: general-purpose
  model: fable                   # 参謀は高推論モデル推奨。実装役は省略（セッション継承）で可
  run_in_background: true
  prompt: |
    あなたは <プロジェクト名> の参謀（技術戦略担当）です。日本語で回答してください。
    プロジェクト: <絶対パス>
    仕様書: <パス>（必ず全文を読むこと）
    制約: <bun 必須、など>
    依頼: <初回タスク。番号付きで明確に>
    回答時は必ず公式ドキュメントで裏どりし、出典 URL を添えること。記憶に頼らない。
```

実装役の起動プロンプトには必ず含める:

- 担当ファイル集合（**担当外は編集禁止**）
- 割り当てタスクのみ対応、スコープ外の「ついで修正」禁止
- 担当分を 1 コミット（`git add -A` 禁止）、コミットメッセージは git-ops 規約
- 完了時は「変更ファイル一覧 + 検証コマンドと結果」を返す

複数実装役を並列起動する場合は、task-orchestration の原則どおり**ファイル集合が重ならないグループ**に束ねてから起動する（task-orchestration では `Task` ツールと表記されるが、本環境の `Agent` ツールと同等）。

## 3. 往復運用（SendMessage）

召喚後の対話はすべて `SendMessage` で行う。宛先は起動時の `name`。生存確認・宛先確認は `ListAgents`。`SendMessage` / `ListAgents` が deferred tool の環境では、先に `ToolSearch`（`select:SendMessage,ListAgents`）でロードする。

司令塔からのメッセージで守ること:

- **裏どり指示を毎回明記**: 「公式ドキュメントで裏どりした上で結論を出してください（記憶に頼らない）」
- **司令塔側の実測結果を共有し、反証を求める**: 「これと矛盾する結論があれば必ず指摘してください」
- **前提が変わったら即共有**: 「前提が変わりました。前便の依頼を以下の方針で読み替えてください」
- **進捗確認は確定分の先出しを求める**: 「調査中なら、現時点で確定できた項目だけでも共有してください（優先度は 1) ... 2) ...）」
- 依頼は番号付きの具体的な問いにする。「どう思う？」のような開放質問を投げない

受信側の注意:

- サブエージェントの返信は task notification として**非同期**に届く。届く前に内容を推測・捏造しない。待つ間は司令塔自身の作業（実測・レビュー・別メンバーへの指示）を進める
- 参謀の主張は鵜呑みにせず、コストの低いものは司令塔が実測で検証する（参謀が司令塔の検証穴を突き、司令塔が参謀の誤りを実測で正す、という相互検証が理想）

## 4. レビューと統合

- 実装役の成果は司令塔がレビューする: diff 確認 → 検証コマンド再実行 → 必要なら差し戻し（SendMessage で具体的な修正指示）
- 設計判断が割れたら、参謀に両案の比較と根拠を出させた上で**司令塔が決める**。決定と理由は参謀・実装役に共有する
- セキュリティ・規約など高リスク論点は、参謀とは別の視点に同じ問いを投げて突き合わせる（Codex が使えるなら `mcp__codex__codex`、単発なら `timeout 1800 codex exec`。詳細は `opus-codex-orchestration` 参照。使えなければ新規サブエージェント）
- 司令塔での検証コマンド再実行は、該当実装役のコミット完了報告を待ってから行う（編集中の作業ツリーで走らせない）

## 5. 解散とコスト管理

- 返信が届いた（turn が完了した）後も、`SendMessage` で文脈を保持したまま対話を再開できる。「返信 = 終了」ではない
- 解散を決めたメンバーには追加送信しない。明示的な kill は不要で放置でよい
- 常駐メンバーは必要最小限に: 標準編成は参謀 1 + 実装役 1〜3。参謀を人数分立てない
- 長丁場では、参謀への依頼をまとめ書きする（1 便に複数論点を番号付きで束ねる）ことで往復回数を減らす

## 6. 他スキルとの使い分け

| 状況 | 使うもの |
| --- | --- |
| 同じ相手と何往復も相談・レビューしたい | **このスキル**（常駐 + SendMessage） |
| 独立サブタスクを一発並列で捌きたい | `task-orchestration`（使い捨て fan-out） |
| プラン・SOW の多視点レビューだけしたい | `plan-digger` |
| Codex / Cursor 等の外部エージェントをペインで統括 | `herdr` |
| Codex を下請けにした大規模開発 | `opus-codex-orchestration` |

併用可: このスキルの実装役の中で、さらに task-orchestration 的な一発 fan-out を使ってよい。

## チェックリスト

### 編成時

- [ ] 各メンバーに `name` を付け、`run_in_background: true` で起動した
- [ ] 参謀プロンプトに「公式ドキュメント裏どり + 出典明記」を含めた
- [ ] 実装役の担当ファイル集合が互いに重ならない
- [ ] 編成（誰が何を担当するか）をユーザーに一言で報告した

### 運用中

- [ ] 前提変更を全メンバーに共有した
- [ ] 返信を待つ間、司令塔自身の作業を進めた（返信内容を推測していない）
- [ ] 参謀の結論のうち検証可能なものを実測で確認した

### 完了時

- [ ] 実装役の全コミットをレビューした
- [ ] 検証コマンド（type-check / lint / build 等）を司令塔側で再実行した
- [ ] ユーザーへの報告に各メンバーの成果と残ステータスを対応づけた
