# フローを組み立てる

## 原資料から対応を作る

資料ごとの識別子・タイトル・URLまたはpath・該当箇所を記録する。実装を根拠にする場合は参照pathと確認revisionを残す。資料の記載、実装確認、提案、未確認を分ける。

各工程について開始条件、担当、入力、作業、出力、次工程、分岐/例外を拾う。Beforeの各工程をAfterの「残す」「アプリへ移す」「支援する」「条件付きで追加」「廃止する」に対応させる。実装済み/将来案/未確認の状態はこれと別に持つ。

変更なしの人の仕事はAfterにも残す。アプリが案を作っても人の確認・承認は消さない。実装や運用が確認できない外部システム連携を、自動化済みと扱わない。

## IDと表示

案件 `projectId`、フロー `id`、工程 `id`、フロー間 `gap.id` を固定する。表示番号・タイトル・順序の変更ではIDを作り直さない。新規IDに既存工程の番号を再利用しない。各targetType内のIDはproject全体で一意にする（工程IDはフローごとの連番だけにしない）。BeforeとAfterのカードを別対象にする場合も別IDを使い、対応はrow.idで表す。

starterの正確な入力形は `assets/starter/public/flow-data.json` を読む。別方式のschemaを作ってstarterにそのまま渡さない。分岐や統合で表現力が不足する案件ではschemaとrendererを一緒に拡張する。

対応が1対多/多対1なら参照元IDの配列を持たせ、同じBeforeを重複計上しない。番号を詰めて対応関係を壊さない。表示フィルタを付ける場合は省略中の工程数を示し、「すべて」に戻せるようにする。

フロー間コメントは画面上の第n番目の隙間ではなく、固定gap.idと接続するフローIDに紐づける。接続自体が変わったら新しいgapとして作り、古いコメントは履歴に残す。

## 数字の説明

工程数は工数や時間削減率ではない。計数単位（1件/1日/1バッチ）、対象範囲、条件、追加作業を先に定義する。「紙ならスキャン」「案を確認する」等を無条件に純増と数えない。

時間根拠がない場合は時間効果を表示しない。人に残る作業、アプリに任せる作業、実装状態の比較で伝える。条件付きの将来案を現状の実績集計に混ぜない。

## 改訂

flow-dataを変更する前に既存IDとの対応を照合する。削除・統合された工程のコメントを別IDへ自動転付しない。元対象が消えてもDBと履歴を保持し、必要なら「旧対象」として閲覧導線を用意する。書き換えたデータと別の生成HTMLが食い違う状態を残さない。
