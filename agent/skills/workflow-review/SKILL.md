# Workflow Review

業務の変化を確認する画面と、その場所に紐づく議論を作る。フロー比較とHTML要素フィードバックの2モードは、同じコメント・Done履歴の仕組みを使う。案件の内容とコメントDBをテンプレートから分離し、改訂しても議論を失わない。

## 依頼を具体化する

- **業務フロー**: 資料、ヒアリング、実装を整理し、Before/Afterと工程・フロー・フロー間コメントを作る。[フロー設計](references/flow-model.md)を読む。
- **HTML要素フィードバック**: 開発者ツールのように要素を選び、その場所にコメントする。既存サイトの見た目を保って組み込む。[要素選択](references/element-feedback.md)を読む。
- 両方なら共通のprojectIdとAPIを使う。単なる静的図や文言修正にはコメントシステム一式を追加しない。

対象資料・HTML・利用者・保存先・公開範囲のうち、成果物を左右し、現在の依頼や既存設定から決められない点だけヒアリングする。既知の回答は再確認しない。材料が足りない工程は「未確認」として作成を進め、創作で埋めない。

標準は自分たちが管理するHTMLへの組込み、ローカル検証、共有DB対応まで。**公開はユーザーが指示した場合だけ**実行する。スキル利用を、公開・クラウド契約・外部投稿の許可と解釈しない。

## 作成と組込み

1. フロー画面と新規のコメントUIには[デザインとグリッド](references/design-system.md)を適用する。デジタル庁の公式仕様と、このスキル独自の運用値を区別する。要素フィードバック導入だけなら、対象サイト全体を再デザインしない。
2. 新規案件には `python3 scripts/init_project.py /absolute/output/path` をスキルディレクトリから実行する。既存ディレクトリを上書きしない。生成後の起動・保存先・共有への接続は[実行と共有](references/runtime.md)に従う。既存アプリには必要なmodule/APIだけ組み込む。
3. サンプルを案件データへ置き換える。projectId、工程・フロー・要素のIDは表示名や配列位置から独立させる。既存案件の更新時はIDを維持し、DBを再作成しない。
4. [コメント契約](references/comments.md)に従って保存・初回名前・Done理由・閉じる操作を揃える。localStorageは名前の補助に使い、共有コメントの保存先にしない。
5. ローカルで実ブラウザを使い、作成→再読込→Done理由保存まで確認する。追加・変更したモードの[検証項目](references/validation.md)を選び、失敗した箇所を直す。APIだけ通っても画面確認済みと呼ばない。

## 引き渡し

起動URL、生成元・データ・DBの場所、更新方法、実施した検証と未確認の共有環境を示す。公開依頼がなければローカル成果物まで渡す。将来再利用するためのコードを元案件のローカルパスや過去タスクに依存させない。

レビュー・実証評価を求められた場合は、利用可能な独立executorに架空資料で試してもらい、実際の成果物を検査する。指定モデルが使えない場合は正直に明記する。通常の使用ごとに特定モデルや相互レビューを必須にしない。
