# Local Preview Start

対象のcheckoutから開発サーバーを起動し、ユーザーが使えるURLと画面を確認する。ポートが開いたことと、目的のページが動くことを分けて確認する。

## 起動方法を決める

- 現在のcwd、プロジェクトの指示、既存の起動手順と設定を読む。monorepoでは対象アプリを特定する。現在のページや直近の会話から一意に決まれば、その解釈で進める。
- README、package scripts、lockfile、既存の設定からruntimeと起動コマンドを選ぶ。特定のframework、package manager、ポート、テナントを共通の既定値にしない。追加のCLIフラグは実環境のhelpで確認する。
- 必要なenvはキーの有無と取得方法を確認し、値を出力しない。既存のbootstrapや、利用可能なenv取得スキルを必要なときだけ使う。秘密値の推測、別プロジェクトからの無断コピー、認証方式の変更で起動を通さない。
- 起動に必要な既存手順は依頼の範囲で実行する。データ初期化、migration、外部API利用などの副作用が含まれる場合は、その操作が既に承認されているかと接続先を確認する。既存の許可で足りなければ、その操作だけを確認し、独立した準備は続ける。

## 既存プロセスを確認して起動する

- 指定ポートのlistenerと、既存サーバーの起動元checkout・コマンドを確認する。同じ対象の正常なサーバーがあれば再利用する。
- 別プロジェクトや不明なプロセスを停止しない。ポート変更が可能ならアプリが対応する方法で空きポートを選ぶ。指定ポートが必須なら競合を報告し、停止の許可が必要な対象だけを確認する。
- サーバーは応答後も生存する実行環境で起動する。Orca管理下では利用可能なOrca CLIと現在のガイドに従い、対象worktreeのterminalを使う。それ以外は利用可能な持続するterminalやprocess managerを使う。既存のユーザー作業用terminalへ割り込まない。
- readinessと起動ログから実際のURLを取得する。host・port・base path・必要な依存サービスを確認し、起動直後の一行だけで成功と判断しない。

## URLと画面を確認する

- 実際のURLへアクセスし、HTTP応答、redirect先、目的のrouteを確認する。HTTP 200でもエラー画面やログイン画面になっていれば、その状態を報告する。
- 利用可能なbrowserで目的のページを開き、runtime errorや不足するAPI・DB接続を確認する。Orcaの内蔵browserを使う場合は、そのガイドのbrowser referenceを読む。browserを操作できなければHTTP確認までの結果と未確認の画面を分ける。
- tenantやテストセッションが必要な場合は、プロジェクトの正規の取得・作成手順を使う。ページを開く依頼を、候補者データ作成、採点、実音声テストやlive DB書き込みの許可に広げない。
- emulatorや依存サービスが起動できなければ、静的画面、API、DB保存の確認結果をそれぞれ報告する。画面だけを見て保存まで正常としない。

## 引き渡し

対象checkout・アプリ、開くURL、起動コマンド、サーバーを維持するterminalまたはprocess、確認できた画面と残る制約を簡潔に返す。変更した設定やファイルがあれば明記する。passcodeなどの認証情報はプロジェクトの扱いに従い、公開レポートやログへ転記しない。
