# 技術図解

技術や概念の実際の仕組みを保ち、予備知識のない読者が「何か」「なぜ必要か」「どう動くか」「何が得意で何が苦手か」を理解できる、縦スクロール型のシングルページ図解を作る。単なる要約にせず、専門用語を正確に説明しながら読みやすくする。

ユーザーが指定した対象、読者、用途、出力形式、デザイン、参考資料を優先する。未指定なら、読者は非エンジニア、読了時間は約5分を目安にする。成果物の形式は既存プロジェクトとユーザーの希望に合わせ、公開・共有や特定サービスへの配置を勝手に追加しない。

## 作成の流れ

1. **対象を調べる。** 技術が解決する問題、従来の方法、主要な構成要素、内部の動作、データや処理の流れ、利点の理由、代替手段、制約、よくある誤解を把握する。仕様や現状に左右される事実は利用可能な調査手段で確認し、公式ドキュメント、仕様書、原著、開発元などの一次情報を優先する。根拠が足りない点は推測で埋めず、不明点や情報源間の違いを明らかにする。
2. **読者の理解順に組み立てる。** 「問題と必要性 → 全体像 → 内部の仕組み → 実際の流れ → 仕組みから生まれる利点 → 代替手段との違い → 制約 → 要点」の流れを基本にする。対象に合わない節は省き、各節が次の理解につながる一本のストーリーにする。複数の構成を機械的に列挙したり、内部の思考過程を出力させたりせず、完成条件を満たす構成を選ぶ。
3. **関係を図にする。** 時系列はフロー、構成はアーキテクチャ図、階層はレイヤー、比較は比較表、状態変化はBefore/After、因果は因果図など、説明対象に合った表現を使う。誰が何を受け取り、何を行い、次に何を渡すかを追えるようにする。比喩や簡略化を使う場合は、実際の仕組みとの対応と省略した範囲を明示する。核心部分を「AIが判断する」「システムが処理する」のような曖昧な箱に隠さない。
4. **視覚化する。** 縦長の単一ページとして、上から下へ自然に読み進められる構成にする。信頼感、親しみやすさ、技術的な明快さを重視し、装飾より情報の階層と読みやすさを優先する。色だけに意味を持たせず、コントラストとモバイルでの読みやすさを確保する。絵文字は避け、アイコンが必要なら適切なライセンスを確認できる線画などを使う。インタラクションは理解を助ける場合だけ追加し、操作しなくても主要情報が読める状態にする。Web成果物ではキーボード操作と動きの抑制設定も考慮する。
5. **根拠と成果物を確認する。** 重要な事実を出典に照らし、用語・図・本文の整合性、因果関係、比較の公平さ、制約の記載を確認する。ページ末尾に資料名・提供元・クリックできるURLを含む参考資料を置く。生成・実装した成果物は、可能なら実際の表示で文字の読みやすさ、図の対応関係、縦方向の流れ、モバイル表示を確認し、見つかった問題を直す。

途中経過を求められたら、確認できた事実、判断理由、未確定点を共有する。内部の逐次思考は出さない。完成時には成果物の場所、主な内容、確認できたこと、残る不確実性を簡潔に伝える。

## 入力の目安

依頼に応じて、次の情報を使う。指定されていない項目は、成果を大きく左右するときだけ確認し、それ以外は妥当な前提を置いて進める。

- `topic`: 図解する技術・概念・文章
- `context`: 参考URL、資料、利用場面
- `audience`: 読者の知識や立場
- `emphasis`: 特に理解してほしい仕組み、比較、制約
- `output`: 希望する成果物形式、保存先、既存プロジェクト
