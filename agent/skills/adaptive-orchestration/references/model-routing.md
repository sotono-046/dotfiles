# 配役と最新モデルの確認

今回のユーザー指定を最優先にし、指定がない役割には次の既定を使う。役割は維持し、モデルのversionは起動時に更新して選ぶ。

| 役割 | モデル系列・設定 | 担当範囲 |
| --- | --- | --- |
| 司令塔・最終統合 | 最新の利用可能なSol、reasoning effort `high` | 目標、調査方針、計画、分担、採否、進捗、成果物の統合 |
| 判断を伴う実装 | 最新の利用可能なSol、reasoning effort `high` | 原因を見極める修正、複雑な実装、判断を伴うテスト設計 |
| 定型実装・作業 | 最新の利用可能なLuna | 仕様・path・手順が決まった変更、テスト実行、定型部分の修正 |
| 分析・設計相談 | 最新の利用可能なAstra・Opus | 原因仮説、設計案、性能・並行処理の分析、別の観点からの検討 |
| 独立レビュー | 最新の利用可能なSol、reasoning effort `high` | 別コンテキストで要件・差分・検証証拠をread-onlyで確認 |

Luna・Astra・Opusのeffortは、今回の指定と分析の難度に合わせ、対応する設定だけを使う。定型作業に一律でHighを要求しない。Astra・Opusの分析をSolによる独立レビューの代わりにしない。

## 最新版を選ぶ

1. 起動するruntimeのtool schema、providerの現行モデル一覧、CLIの選択肢を確認する。手元のキャッシュは補助に使い、起動可能かは実際のruntimeで確認する。別runtimeのモデル一覧で、そのCLIでも使えると断定しない。
2. 同じ系列で利用できる最新のversionを選び、model IDと必要なeffortを起動引数へ渡す。利用不可・廃止・権限外のモデルは使えないものとして報告する。公開最新モデルが利用枠にない場合は、公開版と今回使用する利用可能版を区別する。
3. aliasは、そのproviderが最新の同系列へ解決すると確認できる場合に使う。推測したslugや、意味を確認できない `latest` を渡さない。OpusはClaude CLIのhelp等が最新モデルのaliasと説明する `opus`、または確認済みの完全なIDを使う。
4. 起動receiptや実行情報が返る場合は、要求したモデル・effortと実際の設定を照合する。不一致や実行情報を取得できない状態を隠さない。

2026-10-05のこの環境では、native schemaにSol `gpt-6.1-sol`、Luna `gpt-6-luna`、Astra `gpt-6-astra` が公開されている。これは確認時点の例であり、将来も同じIDへ固定する指示ではない。Solの司令塔とレビュアーには `high` を指定する。

## 分担の判断

Lunaへ渡すのは、目的、仕様、担当path、手順、検証方法が確定した作業。原因分析・設計・要件解釈を実装中に行う必要があればSol Highが担当する。Lunaが未確定の判断を見つけたら、Solが仕様を決めるか担当を変更する。

Astra・Opusには調査対象、問い、コード・ログ・測定結果を渡し、根拠を伴う仮説と案を求める。併用する場合は、最初の分析を独立に行わせ、Sol Highが相違点を実コードと測定で確かめる。両者の利用が明示されていなければ、論点に応じて必要な担当だけを起動する。

レビューは実装担当と別のSol Highへ渡す。元の依頼、正確なbase/HEAD、対象diff、検証結果を渡し、実装側の結論への同意を求めない。重大な指摘と任意改善を分け、採否と修正配信は司令塔が管理する。

## 指定モデルが使えない場合

モデル、必要なeffort、利用枠、override権限と実行経路を確認する。別versionへの暗黙の切替、モデルIDの捏造、新規API課金や契約の追加はしない。既存の認可範囲で実行経路を復旧する。

任意の分析役が使えない場合は、その事実を示し、利用できる担当で進められる調査・実装・検証を続ける。ユーザーが必須指定した分析や、Sol Highの独立レビューを実施できなければ、その条件は未確認として残し、他の成果を取りまとめる。モデル不足だけを理由に、独立して進められる作業まで止めない。
