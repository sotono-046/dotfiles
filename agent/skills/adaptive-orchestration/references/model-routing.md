# 固定配役表

ユーザーが指定した配役。今回のユーザー指定 > この表の順で適用し、価格や評判から実行ごとに別モデルへ変更しない。人数とタスク分割は仕事に合わせる。

| 役割 | モデル指定 | 担当範囲 |
| --- | --- | --- |
| 司令塔・最終統合 | `gpt-6-astra` | 目標、認可、実行状況、成果物の統合を管理 |
| デザイン | Claude CLI `--model opus` | UI/UX、レイアウト、ビジュアル、操作感の検討と実装仕様。製品コードの実装はLunaへ渡す |
| 実装・修正・テスト | `gpt-5.6-luna`、reasoning effort `high` | 小変更から複数ファイルの実装、リファクタリング、テスト追加・実行・失敗修正まで |
| プラン・高度な理論検討 | `claude-fable-5` と `gpt-6-astra` | 独立した提案と相互反証を行い、実装可能な結論へ統合 |
| 独立レビュー | `claude-fable-5` | Lunaの実装を要件と証拠に照らして検証。修正はLunaへ返す |

Opusはinstalled CLIが提供する`opus` aliasを使う。Opus系統の固定であり、具体的なバージョン固定ではない。実行結果に解決後のモデル名があれば記録する。モデルの優劣を実測した配役ではなく、ユーザーの指定を実行する方針である。

Lunaの`high`は必須。他モデルのeffortは追加指定がなければruntimeの既定を使う。native toolのmodel/reasoning引数、またはinstalled helpで確認したCLI設定を使い、プロンプトに「High」と書くだけで設定済みと扱わない。

## FableとAstraの相互反証

プラン立てや高度な理論検討を依頼されたら、単に一方の案を他方へレビューさせるだけで終えない。確定済み計画の実装だけなら新しい議論は始めない。

1. 同じ目標・制約・一次資料を両者に渡し、相手の答えを見せずに独立案を出させる。各案に前提、根拠、代替案、弱点、確認方法を含める。親がAstraでも、独立したAstraコンテキストを使い、親の予想を答えとして渡さない。
2. 両案を交換し、互いの誤った前提・反例・実装上の穴を証拠付きで指摘させる。反証を踏まえ、自案の修正または根拠を伴う維持を返させる。
3. Astraが論点ごとに採否と根拠を整理して統合する。両者の一致やモデル名を正しさの根拠にせず、検証可能な主張は資料・実験・テストに照らす。未解決の意見差は残す。

既定は独立案1回＋相互反証1往復＋統合。完了条件を左右する未解決点がある場合だけ、その論点に限って追加1往復まで行う。決着不能なら必要な検証やユーザー判断を具体化し、無限に議論させない。成果物には統合案・重要な反証への対応・残る不確実性を含める。

## 担当の境界

- 文書の誤字修正や資料整理など、設計・コード実装を伴わない軽作業は現在の親が直接処理してよい。コード変更は規模によらずLuna Highに渡す。ただし、ユーザーがその作業にも指定モデルの使用を要求した場合は従う。
- デザインを伴う開発はOpusが見た目と操作の仕様を作り、Luna Highがコードにする。必要ならOpusが実画面を確認し、Lunaへ具体的な修正指示を返す。一般的なUI調整のたびに理論検討を追加しない。
- 未確定のアーキテクチャや理論的な判断はFableとAstraで整理してからLunaへ渡す。確定済みの要件まで議論し直さない。
- Lunaで入力不足が判明したら根拠を補う。設計の欠陥や推論上の難問ならFableとAstraへ戻し、解決後にLuna Highが実装を続ける。Sol・Terra等への自動昇格はしない。

## 固定モデルが使えない場合

モデル・必要なeffort・契約枠・override権限を確認し、利用できない指定と理由を伝える。自動で別モデルや有料経路へ置換しない。

今回の固定配役を満たせない担当部分は未完了として、実行経路の復旧または代替モデルの指定が必要なことを示す。親は資料整理など独立した準備を続けてよいが、別モデルの実行を指定担当の完了として扱わない。Fableだけ、Astraだけの検討を相互反証の完了として報告しない。
