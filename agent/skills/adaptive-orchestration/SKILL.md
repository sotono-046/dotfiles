# Adaptive Orchestration

仕事を役割に分類し、[固定配役表](references/model-routing.md) のモデルへ振り分ける。モデルの対応はこの表だけで管理し、実行ごとに選び直さない。これは運用上の配役であり、Fuguの学習済みルーターや性能を再現するものではない。

## 実行可能な構成を選ぶ

最初に依頼の成果物・完了条件と、使えるruntime、モデル、権限、ユーザー指定の時間・利用枠を確認する。モデル一覧は現在のtool schemaやCLI設定を使い、過去の会話のモデル名・価格を前提にしない。秘密の設定値や認証情報は出力しない。

- 明示されたモデルを固定配役表より優先する。それ以外は役割に対応するモデルIDを起動時に指定する。表の更新はユーザーから変更を求められたときに行う。
- 呼び出し元が表の司令塔と異なる場合、公開された委譲機能で計画・分担案・結果評価を司令塔モデルへ依頼し、呼び出し元が実行と認可を管理する。実際のモデルを切り替えたと装わない。直接処理で済む小さい仕事には司令塔の追加起動も不要。
- 固定モデルの利用可否とoverride権限を確認する。使えない場合は表の代替ルールに従い、無言で別モデルに変更しない。
- サブスク枠の利用を求められたら、既存のログイン済みCLIを優先する。CLI起動だけでサブスク課金と断定せず、認証方式を確認する。API課金・新規契約・Fugu等の外部サービス追加は自動で行わない。

| 仕事の条件 | 最初の構成 |
| --- | --- |
| 文書の誤字修正や資料整理など、設計・コード実装を伴わない軽作業 | 司令塔が直接処理 |
| 仕様が確定した実装・修正 | Luna Highに実装と必要な検証を依頼 |
| UI・ビジュアルのデザイン | Opusにデザイン判断と実装仕様を依頼し、コード実装はLuna Highへ渡す |
| 独立した調査や別ファイルの実装 | 担当範囲を分けて必要な人数だけ並列化 |
| プラン立て・高度な理論検討・設計上の難問 | FableとAstraが独立案を出し、相互反証後にAstraが統合 |
| 見逃しの実害が大きい変更 | 固定配役表のレビュー担当へ、実装後に別コンテキストで検証を依頼 |

どの構成でも親が目標・認可・統合を保持する。依頼がコード以外でも同じ判断基準を使う。分担する場合は、担当と理由を一行で伝えて実行し、計画の提示だけで止めない。

## 委譲して結果を受け取る

実際に起動する段階で [実行経路](references/execution.md) を読み、利用可能な経路を選ぶ。同じruntime内の子agentを、別製品の実行として報告しない。

担当には必要な根拠だけを渡す。レビュー担当には元の依頼、対象差分、検証情報を渡し、実装者の結論への同意を求めない。

```text
goal: この担当が返す成果物と完了条件
role / model / effort: 固定配役表の役割・モデル指定値・推論設定
context: 必要な要件・根拠・参照ファイル
workspace: 絶対path、必要ならbranch/HEAD
scope: 担当path、除外path、read-onlyまたは許可された編集
constraints: 既存差分の保護、外部操作の認可範囲
budget: 今回の時間・人数・再試行の上限
ownership: 共有Gitのstage/commitは親が管理。子は実行しない
delegation: 再委譲は原則なし。必要なら理由を親へ返す
return: 成果物、変更path、実施した検証と結果、未解決事項、継続ID
```

人数・時間は依頼規模とホスト上限に合わせて決める。通常は配役に必要な最少人数から始める。プラン・理論検討にはFableとAstraの両方を使い、それ以外は並列化で待ち時間が短くなる独立作業だけ追加する。同じpathへの編集は直列化する。

起動後はsession ID・process ID・出力先を保持して完了まで追う。待機中は親の独立作業を進め、timeoutだけで同じ処理を再送しない。

## 結果に応じて構成を変える

1. 子の報告を実際の成果物と照合し、依頼に対応する検証を行う。多数決やモデルの格だけで正しさを決めない。
2. 入力不足や範囲の誤りなら、根拠を補って同じ担当へ追送する。認証・権限・環境エラーならモデルを強くしても解決しないため、実行経路を直すか親が独立した準備作業を進める。固定担当の代行はしない。
3. 実装が難航したら、固定配役表の切り分け・再設計ルールに従う。Luna Highを別モデルへ自動変更せず、必要な設計判断をFableとAstraへ戻す。
4. 同じ失敗の盲目的な再試行はしない。既定では同一担当への修正依頼は2回までとし、改善がなければ親が原因を切り分け、固定配役を保ったまま再設計や入力補完を行う。上限に達しても完了したと扱わず、未解決条件を示す。

担当の完了条件と必要な検証が満たされたら終了する。任意の改善だけで追加エージェントを起動しない。最後に成果物・検証・残件を返し、実際に使ったモデルと分担を簡潔に添える。利用量を取得できない場合、節約額や消費tokenを推測しない。
