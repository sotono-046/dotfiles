# Adaptive Orchestration

Sol Highが目標・分担・判断・統合を持つ。仕事に必要な判断を見極め、[配役と最新モデルの確認](references/model-routing.md) に従って担当を決める。

## 発動と準備

実装・原因調査・検証を分担する開発や、明示されたチーム作業で使う。短い確認や一行置換など、分担の費用が上回る作業は単独で完了してよい。

最初に成果物と完了条件、対象repository・checkout・branch、既存差分、利用可能なruntime・モデル・権限を確認する。ユーザーがbase branchや独立worktreeを指定した場合は、その指定から作業場所を用意する。特定のprojectやbranchを共通の既定値にしない。

モデル・agent・effortの明示指定を優先する。それ以外は各系列の最新の利用可能版を起動時に確認し、Solの司令塔とレビュアーには `high` を実際の起動設定で指定する。現在の司令塔が該当するSol Highなら、そのまま進める。違う場合は利用可能な委譲機能でその役割を渡し、実際のモデルを切り替えたと装わない。

## 判断の必要度で分担する

| 仕事 | 担当 |
| --- | --- |
| 目標・調査方針・計画・採否・統合 | Sol High |
| 仕様・対象path・手順が確定した定型実装、機械的な置換、テスト実行 | Luna |
| 原因を見極めながら行う修正、複雑な実装、判断を伴うテスト設計 | Sol High。非競合の担当なら別workerへ分ける |
| 原因分析、設計案・仮説の比較、性能や並行処理の難問 | 必要に応じてAstra・Opusへ独立した分析を依頼し、Sol Highが統合 |
| UI/UX・ビジュアル・操作設計の判断 | 必要に応じてOpusを活用し、Sol Highが採否を決める |
| 独立レビュー | 実装担当とは別コンテキストのSol High。read-onlyで要件・差分・検証を確認 |

コード変更というだけでLunaへ渡さない。新しい設計判断や未確定の原因を含む場合はSol Highが担当し、切り出せる定型部分だけLunaへ渡す。Lunaが仕様の不足を見つけたら、推測で埋めずSolへ返す。

Astra・Opusは、調査を深める必要があるときに使う。両者で独立に分析すると有益な場合や、ユーザーが両者を指定した場合は併用する。すべての作業で両方を必須にしたり、Fableなど指定のない相談役を追加したりしない。

## 調査・計画・実装・検証を回す

1. まずコードベースと既存の測定・ログ・テストを調べる。問題に関係する呼び出し経路、状態遷移、待機、外部依存を追い、事実・原因仮説・未確認事項を分ける。深い分析はAstra・Opusへ分担する。
2. Sol Highが分析結果を根拠と照合し、原因、変更方針、担当path、回帰リスク、検証方法を計画にする。性能目標では測定の開始・終了点、対象条件、必要な上限を定義し、平均値を最長値の代わりにしない。
3. 計画を実装し、変更に対応するテストと必要な実測を行う。修正前後を同じ条件で比べ、測定が変更後のコードを対象にしていることを確かめる。
4. 未達や失敗があれば、証拠から原因仮説と計画を更新して再度実装・検証する。同じ失敗を盲目的に再試行しない。任意のレビュー回数だけを終了条件にせず、依頼された目標と必要な検証を満たすまで続ける。
5. 最終差分と検証結果を、別コンテキストのSol Highがread-onlyでレビューする。現在のHEADと未コミット差分を対象にし、古いレビューを変更後の承認に使わない。重大な指摘は原因に応じた担当へ返し、変更箇所と関係する条件を再検証する。

「徹底的な調査」の指示は、根拠を得てから計画・修正へ進む指示として扱う。無関係なコード全体の監査へ広げない。最長時間などの数値、base branch、測定環境は今回の依頼から取り、別の作業へ引き継がない。

## 配信から結果確認まで管理する

実際に起動するときは [実行経路](references/execution.md) を読む。Orcaを利用でき、分担が有効ならOrcaの配信・完了待ち・結果統合を積極的に使う。主なworkerはCodex、Opus分析はClaude等の利用可能な経路で実行する。piの利用を既定にしない。

```text
goal: この担当が返す成果物と確認可能な完了条件
role / model / effort: 役割、確認済みのmodel ID、推論設定
context: 元の要件、必要な根拠・参照ファイル
workspace: 絶対path、branch、base/HEAD、既存差分
scope: 担当path、除外path、read-onlyまたは許可された編集
constraints: 保護する条件、外部操作の認可範囲
validation: 検証コマンド、測定条件、必要な証拠
ownership: 共有Gitのstage/commit owner。子はGO前に実行しない
return: 成果物、変更path、検証結果、未解決事項、継続ID
```

独立して進められる調査・非競合の実装は、必要な最少人数で並列化する。同じpathへの編集と共有indexのstage/commitは直列化する。委譲の送信やDone表示で完了とせず、成果物、実行結果、必要な実測を司令塔が確認する。

## 終了

依頼された目標と必須検証を満たし、重大なレビュー指摘が解消したら完了する。任意改善だけでループを延長しない。権限・環境・実行予算により達成を確認できない場合は、その制約と未達・未確認の条件を明記する。未完了を成功として扱わない。

最後に成果物・検証・残件と、実際に使用したモデル・effort・分担を簡潔に返す。指定した起動引数だけで実行モデルを確定しない。利用量を取得できなければ、節約額や消費tokenを推測しない。
