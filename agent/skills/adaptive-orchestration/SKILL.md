# Adaptive Orchestration

仕事を役割に分類し、[固定配役表](references/model-routing.md) のモデルへ振り分ける。モデルの対応はこの表だけで管理し、実行ごとに選び直さない。これは運用上の配役であり、Fuguの学習済みルーターや性能を再現するものではない。

## 発動の目安

通常のコード実装・修正・原因調査では使う。「チームで」「分担して」「レビュー込みで」「オーケストレーションして」などの明示があれば規模を問わず使う。質問への回答、read-onlyの短い確認、指定値どおりの一行置換など、分担が成果を変えない作業では使わない。

## 実行可能な構成を選ぶ

最初に依頼の成果物・完了条件と、使えるruntime、モデル、権限、ユーザー指定の時間・利用枠を確認する。モデル一覧は現在のtool schemaやCLI設定を使い、過去の会話のモデル名・価格を前提にしない。秘密の設定値や認証情報は出力しない。

- 明示されたモデルを固定配役表より優先する。それ以外は役割に対応するモデルIDを起動時に指定する。表の更新はユーザーから変更を求められたときに行う。
- 呼び出し元がSolでない場合、公開された委譲機能で計画・分担・採否・統合をSolへ依頼する。呼び出し元はhost上のtool実行と、ユーザーが認可した範囲の強制だけを担う。実際のモデルを切り替えたと装わない。
- 固定モデルの利用可否とoverride権限を確認する。使えない場合は表の代替ルールに従い、無言で別モデルに変更しない。
- サブスク枠の利用を求められたら、既存のログイン済みCLIを優先する。CLI起動だけでサブスク課金と断定せず、認証方式を確認する。API課金・新規契約・Fugu等の外部サービス追加は自動で行わない。

| 仕事の条件 | 最初の構成 |
| --- | --- |
| 文書の誤字修正や資料整理など、設計・コード実装を伴わない軽作業 | Solが直接処理 |
| 実装・修正・原因調査を伴うbug fix | SolがLunaへ作業を渡し、完了後にAstraが独立レビュー |
| UI・ビジュアル・操作デザイン | 判断が必要ならOpus 5.5とFableへ独立に相談し、Solが統合、Lunaが実装、Astraがレビュー。指定値どおりの置換だけなら相談不要 |
| 独立した調査や別ファイルの実装 | Solが範囲を分け、Lunaを必要人数だけ並列化 |
| プラン立て・設計上の難問 | Solが計画を作る。視覚・操作デザインを含む論点だけOpus 5.5とFableへ相談 |

どの構成でもSolが目標・認可・統合を保持する。依頼がコード以外でも同じ判断基準を使う。分担する場合は、担当と理由を一行で伝えて実行し、計画の提示だけで止めない。

## 委譲して結果を受け取る

実際に起動する段階で [実行経路](references/execution.md) を読み、利用可能な経路を選ぶ。同じruntime内の子agentを、別製品の実行として報告しない。

担当には必要な根拠だけを渡す。Astraには元の依頼、対象差分、検証情報を渡し、Lunaの結論への同意を求めない。

```text
goal: この担当が返す成果物と完了条件
role / model / effort: 固定配役表の役割・モデル指定値・推論設定
context: 必要な要件・根拠・参照ファイル
workspace: 絶対path、必要ならbranch/HEAD
scope: 担当path、除外path、read-onlyまたは許可された編集
constraints: 既存差分の保護、外部操作の認可範囲
budget: 今回の時間・人数・再試行の上限
ownership: 共有Gitのstage/commitはSolが管理。子は実行しない
delegation: 再委譲は原則なし。必要なら理由をSolへ返す
return: 成果物、変更path、実施した検証と結果、未解決事項、継続ID
```

人数・時間は依頼規模とホスト上限に合わせ、必要な最少人数から始める。デザイン判断にはOpus 5.5とFableの両方を使い、それ以外は並列化で待ち時間が短くなる独立作業だけ追加する。同じpathへの編集は直列化する。

## 結果に応じて構成を変える

1. Solが子の報告を実際の成果物と照合し、依頼に対応する検証を行う。多数決やモデルの格だけで正しさを決めない。
2. 入力不足や範囲の誤りなら、根拠を補って同じ担当へ追送する。認証・権限・環境エラーならモデルを強くしても解決しないため、実行経路を直す。固定担当の代行はしない。
3. Lunaの作業が難航したらSolが原因を切り分けて再分割する。視覚・操作デザインの欠陥ならOpus 5.5とFableへ戻し、統合した指示をLunaへ渡す。
4. AstraのblockerはSolが根拠を確認し、実装上の問題はLunaへ、デザイン判断の問題はOpus 5.5とFableの両方へ返してからLunaへ修正を渡す。同じ失敗の盲目的な再試行はせず、既定では修正依頼を2回までとする。改善がなければ未解決条件を示す。

担当の完了条件と必要な検証が満たされたら終了する。任意の改善だけで追加エージェントを起動しない。最後に成果物・検証・残件を返し、実際に使ったモデルと分担を簡潔に添える。利用量を取得できない場合、節約額や消費tokenを推測しない。
