# 検証ツールの扱い

資料の作成とexplainer本体の変更は別の作業範囲である。まず利用中の版・CLIヘルプ・実コードから問題を確認する。以下は修正候補であり、未対応の機能を存在するものとして呼ばない。本体の修正が依頼に含まれない場合、成果物側で対処できる範囲を進め、ツール側の制約と未確認範囲を残す。

## 対応する問題だけ確認する

| 問題 | 確認と修正の方針 |
| --- | --- |
| テーマ指定 | light・dark・systemを設定として扱えるか確認する。依存先の共有ビルダーを無断で固定テーマへ書き換えない |
| 折りたたみの検査 | 属性付き・入れ子のdetailsも検査用コピーで開く。可能ならDOMで操作し、元資料へ反映しない。開いた版と閉じた版を区別して確認する |
| 日本語の折り返し | 描画時の改行と実際の文字欠落を区別する。日本語と英語識別子の双方を含む例で照合する。空白の一律削除で別ラベルが一致しないか確認する |
| 図の再検査 | 図・事実シート・生成SVG・検証器・依存版・テーマ・viewport等、結果に影響する入力のハッシュを記録し、同じ条件の結果だけ再利用する |
| 並列実行 | worker数を設定可能にし、実行環境に合わせて上限を決める。個々の異常終了・起動失敗と検査結果を回収する |
| checksの成功判定 | コマンドの終了コードと期待出力の両方を確認する。異常終了前に期待行を出したケースを成功にしない |
| 検査省略 | 省略した検査は未実施として表示する。検証済み結果を再利用した場合は対象入力と取得元を示す |

キャッシュや警告除外を追加するなら、古い検証結果が変更後に流用されるケースを確認する。引用一致・事実シート一致は説明の意味やruntime到達性まで保証しない。

## スキルを改訂するときの評価例

大幅な改訂では、元の依頼と架空コード・ログだけを独立した読み手へ渡す。下の観点は評価側に持たせ、期待する答えを実行側へ教えない。編集成果物は一時ディレクトリへ置き、実システムや元資料を変更させない。

- 分類器の説明で、優先規則・条件付き同意・判定失敗の扱いを区別できるか。
- 「図が粗い」「非技術者向けに」「ライトモードで」と追加指示した後、条件とコード根拠を保って更新できるか。
- 図の並べ替え・ページ分割後も、以前の工程IDから同じ工程へ辿れるか。
- テキスト試験と音声試験、異なる配信SHA、欠測を混ぜた材料から、比較できる範囲を正しく説明できるか。
- 並列処理・棄却・再生成を含むログから、測れた区間と原因候補を区別できるか。
- 本体改修を頼んでいない資料作成で、依存スキル・共有ビルダー・本番の計測設定を変更しないか。

図の枚数や定型文の一致だけで採点せず、作られた条件図・工程対応・分析の根拠を確認する。実施していない評価を合格として報告しない。
