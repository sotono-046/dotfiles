# 工程と根拠の対応

複数ページや分析で工程を参照する場合は、既存の対応表・JSONなどを再利用する。小さな解説なら本文の表で足りる。新しい形式を増やすためだけに移行しない。

## 記録する内容

| 対象 | 必要な情報 |
| --- | --- |
| 資料 | 対象repository、調査SHA、関係する未コミット差分、図とページの所在 |
| 工程 | 図ID、工程ID、平易な名称、入力、分岐条件、採用・棄却・失敗時の動作 |
| コード根拠 | 調査SHA、ファイル、行またはsymbol、caller、実行に必要な設定 |
| 観測 | run・session・request・attemptの識別子、ログイベント、開始・終了の境界、値・単位 |
| 計測対象 | 実際に動いたapp・gateway等のSHAまたは確認できた版、環境、条件、取得元 |
| 根拠の状態 | コード確認、実行観測、原因仮説、未確認。必要なら同じ工程に複数の状態を持たせる |

図ID・工程ID・コードsymbol・ログイベント名は同じものではない。対応が確認できたものだけ結ぶ。設定の既定値と実行時の有効値も区別する。

## 遅延を説明する

1. 何から何までを測るかを先に固定する。テキスト応答の完成と実音声の開始は別の境界として扱う。
2. 同じrequestでも試行を分ける。初回生成、棄却、再生成、配信、音声準備の記録を保持する。識別子が不足する場合は、確実に対応付けられる範囲だけ使う。
3. 同一の時計・計測系で得た時刻を用いる。異なる時計の差を、そのまま所要時間としない。並列区間、依存関係、欠測を示す。
4. 計測済みの区間を図に重ね、設定上限や原因候補は区別して表示する。全体時間から既知の時間を引いた残りは、特定工程の実測値ではない。
5. 改善候補は、観測した症状、工程ID、根拠、原因仮説、変更案、確認方法を対応させる。実害・頻度・短縮可能性で順番を決め、実測順と調査優先順を混同しない。

例えば「生成後の検査が遅い」という仮説は、全文受信と検査完了の両方が同一試行で記録されるまでは確定しない。後段で再生成していれば、その時間を検査単独の所要時間にしない。

## 更新する

- 図の位置・説明文を変えても工程IDは維持する。工程を廃止したら参照先に廃止と代替先を示す。
- コード根拠が変わった工程から、条件・失敗時動作・図・引用を再確認する。調査SHAを変えただけで全工程を確認済みにしない。
- 改善前後のrunは別記録にし、版・環境・計測境界の一致を確認して比較する。目標値は今回の依頼から取り、過去案件の秒数を既定にしない。
- 欠測の補完、測定境界の変更、タイムアウトの扱いが変わった場合は、見かけの改善と区別できるように記録する。
