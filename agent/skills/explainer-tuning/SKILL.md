# Explainer Tuning

読み手が「どの条件で何が起きるか」「どこで待ったか」「何を変えるべきか」を判断できる解説を作る。explainerの作成・検証手順に、判断フローと実測を追うための指示を追加し、yomiyasuで意味と条件を保った日本語に整える。

## 前提スキルと適用範囲

1. 利用可能なスキル一覧から `explainer` と `yomiyasu` の実際の `SKILL.md` を解決し、両方を読む。同じ作業中に読んだ内容は再利用する。`metadata.required-skills` は依存関係の記録であり、自動読み込みを保証しない。
2. 一覧になければ、今回指定された配置先、接続済みプラグイン、会話で確認済みのローカルcheckoutを調べる。explainerの導入元は [mizchi/explainer](https://github.com/mizchi/explainer), yomiyasuは[nanaism/yomiyasu](https://github.com/nanaism/yomiyasu)。古い個人パスや版を固定せず、実際に使った配置と版を確認する。
3. 見つからない前提は明示し、材料の整理は続ける。前提スキルを読めないまま適用済みと報告せず、未承認のインストールや別スキルへの置換はしない。

ユーザーの形式・読者・テーマ・編集範囲を優先する。このスキルの既定は判断用の解説で、クイズ・演習は必要な場合だけ加える。短い説明にHTMLや多数の図を強制しない。実装変更・新規計測・外部公開は、今回の依頼に含まれる場合だけ実行する。

## 読み手と説明の粒度

- 会話と既存資料から、読者、判断したいこと、既知の知識、希望する表示を拾う。未指定なら、本文は非技術者が動作を判断する説明とし、技術情報は補足へ分ける。この仮定は短く示す。
- ペルソナでは本人の発言と推測を分ける。明示的な追加指示は今回の設定に反映し、既存ペルソナが編集範囲に含まれる場合は確認済みの好みとして更新する。経験年数や知識を創作しない。
- 本文は具体的な入力例、分類・採否の条件、その後の動作を対応させる。条件式の否定、優先順位、例外、機能設定、判定に失敗した場合の動作を、平易な言い換えで落とさない。
- 全体図で入口と出口を示し、読み手の判断に必要な処理を個別図へ展開する。必要な図の数は分岐の内容で決める。「AIが判断」「チェックする」だけの箱で重要な条件を隠さない。分類器なら、何を手掛かりに分類するか、いつ結果を採用しないかも示す。

## 根拠と工程ID

重要な判断は、本文・図・根拠を対応付ける。コードの定義だけで実行を断定せず、caller、設定、採用先も調べる。調べたSHAと未コミット差分の有無を記録し、実測がある場合は計測対象の版を別に持つ。

フローの位置を議論する資料には、作成時から図IDと工程IDを付ける。例は `FLOW-014` と `FLOW-014-D`。既存IDを優先し、表示名・並べ替え・ページ分割で変えない。廃止したIDは再利用せず、分割・統合した工程には旧IDとの対応を残す。HTMLなら工程へのリンクも確認する。

工程とコード・観測を複数資料で共有する場合、または遅延を分析する場合は [工程と根拠の対応](references/flow-evidence.md) を読む。対応データから図・索引・分析表を生成できる構成を優先し、別々に手書きして整合性を失わせない。

## 実測と資料の更新

- 計測値があれば、開始・終了の境界、試行回数、欠測、タイムアウト、棄却と再生成を工程に対応させる。ログイベント名と実際の動作が一致するかを確認する。
- 並列処理と直列の待ちを区別する。全体時間を決めた経路が確認できる場合だけ示し、並列区間の時間を単純に加算しない。設定上の待機上限を実測値として扱わない。
- 実測・コード上の条件・仮説・未確認を本文と図で見分けられるようにする。未測定の工程へ時間を割り振らず、図と事実シートが一致しても原因を証明したとは言わない。
- 改善前後は同じ計測境界・条件で比較する。対象SHAや配信版が異なれば、その差と比較できない範囲を示す。既に外れた経路を現行の原因として数えない。
- 更新では影響する工程・根拠・図を再確認する。既存の説明やIDを無関係に再構成せず、根拠が古くなった箇所は再確認するまで明示する。

## 表示・検証・引き渡し

HTMLを作る場合、指定がなければライトモードを既定にし、本文と技術補足を分ける。長い資料は問いや処理群ごとにページを分ける。既存ビルダーがテーマ指定に対応するか確認し、存在しないCLIフラグを作らない。テーマ指定のためだけに共有explainer本体を改変せず、成果物側で設定できる方法を選ぶ。

explainerで図の事実シート、コード・出力の引用、HTMLを検証し、yomiyasuで日本語を推敲する。推敲で図の条件・ラベルを変えたら、対応する根拠と図も確認する。HTMLの作成・修正では利用可能な `ui-screenshot` を読み、実表示の必要な状態を撮影・目視確認する。静的図の描画シートも確認する。

検証は変更した範囲を中心に実行する。検証器やビルダー自体の問題に当たった場合は [検証ツールの扱い](references/tool-validation.md) を読む。検査省略・警告除外・過去の結果を、今回の検証成功へ置き換えない。

最後に、成果物へのリンク、判断できること、実施した検証の範囲、未確認事項を短く伝える。表示検査・引用照合・実行観測・性能目標の達成を分けて報告する。
