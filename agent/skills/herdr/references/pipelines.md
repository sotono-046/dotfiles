# 編成プリセット

`Helix`、`P-A`〜`P-F`、`M-#` の指定があるときの追加ガイド。通常の編成は [役割](roles.md) と [運用](operations.md) を使う。プリセットを選んでも人事の担当作成とPMの作業指示を分ける。

## 選び方

| 指定 | 用途 | PMが人事へ依頼する担当 | 進め方 |
| --- | --- | --- | --- |
| P-A 標準 | 中規模の開発・資料作成 | 必要な実装役、必要時のレビュー・検証役 | PMが仕事を分解し、非競合の作業を配信。成果と完成条件を照合 |
| P-B 専門実装 | 単一repoの難しい実装・大きなrefactor | 専門実装役、独立レビュー役 | 実装・focused検証・必要なE2Eを一続きで扱い、PMが採否を判断 |
| P-C 複数仕事 | 複数workstreamの並行進行 | 仕事別PM、実行役、必要な全体調整役 | 各PMが配下を指揮。全体調整役が仕事間の依存・編集範囲・統合順を管理 |
| P-D 設計相互レビュー | 基盤やarchitectureの難しい判断 | 設計担当、独立レビュー担当、必要な実装役 | 設計案と反証を別担当で検討し、PMが根拠を照合して決定 |
| P-E 並列調査 | 技術選定・原因調査 | 必要な観点別の調査役 | 一次情報・実験・事例調査などで分担し、PMが矛盾・鮮度・再現性を照合 |
| P-F 受入検証 | 実装済み成果物の独立検証 | 実装に参加していない検証役・レビュー役 | PMが対象SHAと合格条件を固定し、検証証拠と要件照合で判定 |

Helixだけが指定された場合は上表から用途に合う最小構成を選び、理由を一行で伝える。preset名で固定人数や2×2レイアウトを強制しない。必要な担当だけを人事が追加する。

旧呼称のSupervisorは必要時の全体調整役、CommanderはPM、Specialist / Implementer / Researcher / Validatorは実行役に対応する。モデルを理由にPMや全体調整役を重複起動しない。モデルは [roles.md](roles.md) に従って現行runtimeで確認する。

## Mission mapping

| 指定 | 用途 | 構成 |
| --- | --- | --- |
| M-1 | 問題の整理・修正・前後比較 | P-A |
| M-2 | 認可された自社security診断 | P-C |
| M-3 | agent改善と評価 | P-D |
| M-4 | 組織GitHubの棚卸し・優先順位 | P-E |
| M-5 | 権限と記録の監査 | P-F |
| M-6 | 事業計画・企画書 | P-E後にP-F |
| M-7 | 未知領域の調査 | P-E |

別途指定されたmission YAMLがあれば、そのstages・gates・guardrailsをpacketへ反映する。読めない部分を推測しない。

## 実行と判定

- 予算・同時実行数・修正上限・重い検証の回数をPMが開始前に決める。scope外の問題を自動で追加しない。
- 実装者は自分の独立レビューを兼ねない。P-Dではレビュー担当へ想定解を先に渡さず、反証の根拠を確認する。
- 合格条件は今回の依頼に合わせる。必要なlive確認・E2Eを低レイヤ検査で代替せず、無関係なdeployやPDF出力を追加しない。
- commit・push・merge・deploy・外部送信の権限は今回の依頼から引き継ぐ。preset名だけで広げず、既に得ている認可を再要求しない。
- 内部のrole定義やsecretをIssue・PR・外部サービスへ転載しない。各担当には作業に必要な情報だけを渡す。
- 同じ失敗が続く場合は修正ループを止め、根拠を読み直して方針を再判定する。成果回収・交代・終了は [operations.md](operations.md) に従う。
