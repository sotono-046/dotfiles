# チームを起動する

`herdr start` は、人事・PM・Workboardを準備する短い起動指示。Piの `/herdr` もこの手順を使う。後ろに仕事の内容やruntime指定があれば、その依頼を引き継ぐ。

## 起動手順

1. このスキルの [役割](roles.md)、[運用](operations.md)、[Workboard連携](workboard.md) を読む。対象は現在のrepoとHerdr workspace。明示指定があればそちらを優先し、複数候補から一意に決められない部分だけ確認する。
2. 現在の会話が対象Herdr pane内で動いていれば、この会話をPMとして使う。既に今回の仕事を管理するPMがいればそちらへ引き継ぎ、重複PMを作らない。人事も今回の認可範囲で使える既存担当を優先する。
3. 人事がなければ呼び出し元が起動してroleを渡す。runtimeは明示指定を優先し、未指定なら現在のPMと同じruntimeを第一候補にする。Piには `--kind pi` を使い、モデル・認証・引数は現行runtimeで確認する。Codex専用引数をPiへ流用しない。人間が人事とPMへ直接相談できる配置にする。
4. 対象workspaceにbindされたWorkboardを再利用し、なければ連携手順に従って追加する。auto-syncのOFFを確認する。人事・PM・boardの実IDとrunの保存先を記録する。
5. 仕事が指定されていればPMがカードを作り、必要な担当を人事へ依頼して、認可された作業を配信する。本文が曖昧でも確定している部分は進める。仕事がまだなければ、人事・PM・ボードを準備した状態を示し、目標の相談を受ける。架空の実装taskや不要な実行役は作らない。
6. 起動結果として、PM・人事の場所、board名とID、今回のtask、準備済みと未確認の範囲を短く返す。roleへの応答・配置・仕事完走を区別する。

この指示は今回必要なチームとボードの準備を認可する。commit・push・merge・deployなどは元の依頼の認可範囲を引き継ぎ、起動コマンドだけで広げない。

## 再実行・管理外

繰り返し呼ばれても、人事・PM・board・同じtaskを追加作成しない。registry、boardとカードの実状態、run/task/revision、起動済みpaneを照合して不足分だけ補う。応答喪失時はWorkboard連携の復旧手順を使う。

Herdr管理外では環境変数を偽装せず、スキル・CLI・packetの準備まで進める。実起動は未実施と伝え、対象プロジェクトを開いたHerdr内で同じ指示を使うよう案内する。

## 呼び出し例

| 環境 | 体制だけ準備 | 仕事も渡す |
| --- | --- | --- |
| Pi | `/herdr` | `/herdr ログイン失敗の原因を調べて修正して` |
| Piのスキル呼び出し | `/skill:herdr start` | `/skill:herdr start 人事と実行役もPiで、ログインを修正して` |
| Codex | `$herdr start` | `$herdr start ログイン失敗の原因を調べて修正して` |

他runtimeも、導入済みherdrスキルへ `start` と追加指示を渡す。runtime固有のslash構文が未確認なら、自然文で「herdrスキルのstartを実行して」と依頼できる。
