# 行為の範囲と短い指示

有効な AGENTS.md と今回のユーザー指示を優先する。次はこの dotfiles のショートカットを workflow 間で揃えるための対応表。既に与えられた認可を毎回取り直さない。

| 指示 | 実行範囲・完了地点 |
|---|---|
| `CI見て` / `現状見て` | 状態と失敗原因を調べ報告。修正やremote操作は含まない |
| `PR監視` / `マージまで` / `mergeまで` / `CI通るまで` | CI完了とmerge可能性を確認して停止。これだけで修正・push・mergeしない |
| `直して` / `通して` | 対象の修正と必要な検証。PR更新まで依頼されていればcommit/pushも含む |
| `レビュー指摘対応` | 対象指摘を修正・検証し、必要なPR更新と対応済みthreadのResolveまで |
| `PR更新して` / `pushして` | 対象変更のcommit/pushと新headのCI確認まで |
| `readyにして` | 条件確認後にdraftを解除。mergeは含まない |
| `マージして` / `mergeして` / `マージしていい` | 現在のheadの必須条件を確認してmerge。繰り返し確認しない |
| `OK、コミットPR` | 今回の変更をcommitしPRを作成 |
| `OK` | 直前の具体的な提案を承認し、その範囲で続行 |
| `Issue化して` / `Issue作って` | title/bodyを準備して対象repositoryに作成 |
| `Issue下書き` / `レビューだけ` | 下書き・読み取りだけ。外部投稿や修正は含まない |

複数の指示は合成する。例えば「checks直して、マージまで」は修正と許可されたPR更新後にmerge可能で停止。「マージまでしておいて」のように監視か実行か判別できない語も、会話内の明示merge認可がなければ監視まで進め、mergeだけ保留する。

公開コメント・メール等の送信は明示の送信依頼がある場合に限る。レビュー指摘対応に伴うResolveの認可を新規コメント投稿に拡張しない。merge認可をbranch削除・force push・破壊的cleanupへ拡張しない。
