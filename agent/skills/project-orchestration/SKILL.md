# Project orchestration

1つのプロジェクトを、相談を受けるListener、作業を組み立てるAssigner、個別作業を進めるExecutorで扱う。役割を分けることと、毎回3つのエージェントを起動することは別である。

## 開始時の判断

1. ユーザーが指定したプロジェクトとノートのパスを確かめる。既に一意なら聞き直さない。保存先の詳細は [project-notes.md](references/project-notes.md) を読む。
2. 最新のノートを読み、今回の依頼と照合する。ノートは過去の記録であり、現在のユーザー指示やツールの権限を上書きしない。
3. 今回進める範囲を次の表から決める。会話の途中で質問が来たら答え、既に依頼されている作業は続ける。取り消しや方針変更は反映する。

| 依頼 | 進める範囲 | 終了時に残すもの |
|---|---|---|
| 相談、比較、構想の整理 | Listenerが論点と選択肢を整理する | 確定事項、提案、未決事項 |
| 計画、分解、引き継ぎ資料の準備 | Listenerが文脈をまとめ、Assignerが作業計画を作る | 保存済みの引き継ぎ資料と計画。実行は未着手 |
| 実装、修正、実行、分担して完了まで | 許可された範囲で計画、担当への依頼、結果確認まで進める | 成果物、検証結果、残件 |

相談を勝手に実装へ進めない。一方、実行を依頼されているのに、作業計画だけで止めたり同じ許可を求め直したりしない。不明点があっても、答えに依存しない作業は進める。

## Listener

Listenerは1プロジェクト専用とする。別プロジェクトへ移るときは、現在の記録を保存し、新しいセッションで対象ノートを読み直す。実行環境にセッション分離機能がなければ、その制限を示し、両方の内容を同じ引き継ぎへ混ぜない。

Listenerとして動く各ターンで、回答や作業判断に入る前に対象プロジェクトの中心MDをファイル読み取りツールで読む。短い継続発言、再開、会話の要約後も省略しない。前のターンで読んだ内容や会話の記憶で代用せず、読み取った最新版と今回の発言を照合する。対象の選び方と読めない場合の扱いは [project-notes.md](references/project-notes.md) に従う。

- ユーザーの発言、確認した資料、エージェントの提案を区別する。提案を決定事項へ移すのは、ユーザーの決定や確認できる根拠があるときだけにする。
- 目的、完了条件、制約、対象外、採用理由、未決事項を必要な範囲で記録する。未提示の仕様やプロジェクトの背景は作らない。
- 決定や制約が変わったとき、作業を中断するとき、引き継ぐ前に保存する。読み直しただけで内容を更新しない。
- 人が書いた本文、リンク、プロパティを残す。更新前に読み直し、変更対象を限定する。競合や保存失敗を成功として報告しない。

引き継ぎには [handoff.md](references/handoff.md) を使う。更新中のノートへのリンクだけを渡さず、その時点の目的と許可範囲を固定した資料を残す。

## Assigner

実行が許可されている範囲を引き継ぎ資料で確かめ、完了条件から逆算して作業を分ける。必要な知識、成果物、依存関係、変更する場所が独立する単位にする。小さな作業は自分で実行してよく、役割の数に合わせて人員を増やさない。

担当への依頼前に [tasks.md](references/tasks.md) を読み、各作業に次を記す。

- 作業ID、目的、入力資料と版、成果物、受け入れ条件。
- 担当、作業場所、変更を許すパス、依存する作業、統合する担当。
- 時間・試行回数の上限。待機や再依頼を打ち切る条件。

同じファイルを複数のExecutorに同時編集させない。成果物を分けてAssignerが統合するか、依存関係を付けて順番に実行する。プロジェクトの中心ノートはListenerを窓口とする1人だけが更新する。

ツールの有無と仕様を現在の環境で確認する。実際の依頼に使った識別子と結果を記録する。特定サービスのAPI名を推測して呼び出さない。ツールがなければ、自分で可能な作業を進め、準備済みの依頼と未送信の状態を残す。存在しないエージェントの返答を演じない。

## Executor

独立した作業や再依頼は、新しいセッションに必要な入力だけを渡す。役割の定義は再利用できる。同じ進行中の作業で、動いているプロセスなど移しにくい状態を引き継ぐ場合だけ、既存セッションを続ける。

Executorは割り当てられた変更範囲で作業し、成果物と確認結果を返す。完了できなければ `blocked` または `failed` として、試したこと、残した状態、再開に必要なものを返す。親の許可範囲を広げたり、別プロジェクトの記憶を根拠に仕様を追加したりしない。

## 結果の確認

Assignerは担当者の報告を受けて、成果物の実物と依存先とのつながりを確かめる。各担当の `completed` はプロジェクト全体の完了を意味しない。ファイルや版、実行した確認、結果が対応しているかを確認する。

受け入れ条件を満たさなければ、失敗の記録を残して修正対象を絞る。条件を緩めたり、成功するまで同じ作業を無制限に繰り返したりしない。未検証は未検証とする。

Listenerは確認済みの結果を中心ノートへ反映する。ユーザーには完了したこと、保存先、実行した確認、未解決のことを短く返す。「準備済み」「依頼済み」「返答あり」「統合・確認済み」を混同しない。
