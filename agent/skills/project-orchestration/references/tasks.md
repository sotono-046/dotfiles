# 作業の依頼と結果

## 作業記録

計画時は担当候補と実際の依頼先を区別する。作業IDと試行番号を付け、再依頼でも前の記録を残す。

| 項目 | 内容 |
|---|---|
| task_id / attempt | 作業と今回の試行を識別する値 |
| handoff | 引き継ぎ資料のIDと読める保存先 |
| goal / acceptance | 目的と成果物で確かめる条件 |
| inputs / outputs | 必要な資料の版と出力先 |
| workspace / write_paths | 作業場所と変更を許す範囲 |
| depends_on | 先に必要な作業。なければ空 |
| owner / dispatch_id | 担当と実際の依頼の識別子。未依頼は未設定 |
| limits | 期限、試行回数、費用など今回必要な上限 |
| status | planned / running / completed / blocked / failed |

独立した資料作成なら出力ファイルを分ける。ソースコードの変更なら、共有するファイルや実行環境への影響を確認してから作業場所を分ける。worktreeの有無だけで、DBや設定も隔離されたと判断しない。

## Executorへの依頼

役割、目的、入力、成果物、受け入れ条件、変更範囲、上限を渡す。親の会話全体は渡さず、必要な追加指示をまとめて含める。不要な過去の結論や他の作業の議論を混ぜない。

完了時は次の内容を返すよう依頼する。

```text
task_id / attempt:
status: completed | blocked | failed
artifacts: 保存先と版
changes: 実際に変えたこと
checks: 実行した確認、結果、ログの保存先
remaining: 未完了・未検証のこと
resume: blocked / failed の原因、試したこと、残した状態、再開条件
```

`completed` は当該作業の受け入れ条件を確認できた場合に使う。ファイルを作っただけ、コマンドを起動しただけ、担当が完了と言っただけでは検証済みにしない。

## 待機と再依頼

ユーザーや実行環境の上限を優先する。上限がなければ、着手前に作業の大きさに応じた期限を定め、同じ原因への再試行は1回までを初期値とする。この値はプロジェクト全体の停止時間ではなく、同じ作業への自動再試行回数である。

待機APIの時間切れは作業失敗と同一視しない。実際の状態を確認し、動いている担当へ重複した依頼を送らない。待機は環境の上限内で区切り、変化のない状態を頻繁に照会しない。

期限を超えた場合は状態と成果物を確認し、停止や継続の可否を記録する。以前の担当が停止したと確認できるまでは、同じ変更範囲の担当を重ねない。

不足情報や権限が原因なら `blocked` とし、必要な入力を示す。実行や検証の失敗なら `failed` とし、証拠を残す。再依頼時は原因に応じて入力や方法を修正し、新しい試行として記録する。上限に達したら残件と再開条件を返す。

## 統合確認

Assignerが成果物を読み、個別の条件とプロジェクト全体の条件を確認する。たとえば別々に作った一覧と参照先は、件数だけでなく識別子が対応しているかを確かめる。担当の自己申告と確認できた結果が違う場合は、両方を残す。

最終報告には対象の版、実行した確認、その結果、未検証の範囲を含める。異なる版の検証結果を現在の版の証拠に使わない。
