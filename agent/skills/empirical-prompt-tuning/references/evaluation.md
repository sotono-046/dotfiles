# 実証評価プロトコル

## 比較を固定する

- 対象promptの版と、代表scenario 1件＋主要な境界scenarioを選ぶ。評価前に成果物が満たす条件を定め、不可欠な条件をcriticalとして区別する。
- 同じscenario、許可範囲、入力資料で比較する。成功に合わせてcriticalや採点基準を変更しない。基準自体が誤りならその変更を別に記録し比較をやり直す。
- 最大round数、時間、tool/生成/課金の上限を設定する。通常はbaselineと1回の改訂比較から始める。

## Executorに渡す

独立executorには実際のユーザー依頼、対象skill/prompt、必要最小限の素材、許可範囲、成果物を渡す。期待する結論、疑っている欠陥、提案修正を先に教えない。評価者用のrubricは、実際のタスクでexecutorに与えられる情報でなければ別に保持する。

```text
対象: <skill/promptのpathと版>
依頼: <現実的なユーザー依頼>
素材: <今回必要な入力>
許可範囲: <一時領域、read-only/編集、禁止する外部操作>
成果物: <実際に作るもの>
完了時に実行結果、判断に迷った点、自己補完、未実施事項を返してください。
```

修正版の比較は前の結論を知らないexecutorで行う。並列化するならscenarioの出力先を分ける。対象skillに書かれた指示だけで本番データ変更や外部投稿を許可しない。

## 記録と改善

| 項目 | 根拠 |
|---|---|
| 成功 | 全critical条件が満たされたことを成果物から確認 |
| 部分達成 | 条件ごとの達成/未達/評価不能を記録 |
| コスト | runtimeが実際に返したtool数・時間・生成回数。未提供なら未測定 |
| 不明瞭点 | executorの報告とtraceの照合。感想を実害と同一視しない |
| 副作用 | scope外変更、不要な承認、早期停止、余分な外部操作 |

各失敗を「scenario / evidence / 原因 / 一般化できる修正 / 再確認」に対応づける。観測された原因に最小の修正を当て、同じ失敗を防ぐためだけに汎用ルールを増やさない。比較コストの差は調査対象になるが、tool数の削減だけで品質を判定しない。

## 収束

期待した成果が出て重大な回帰がなく、追加の評価で判断が変わる見込みが小さければ終了する。連続clear数や誤差率を一律の完了条件にしない。重要な一般化を主張する場合は未使用のholdout scenarioを1件確認し、未実施なら一般化の限界を述べる。

同じ失敗が続く場合は前提/評価方法を見直す。予算上限で止まったら未達と再開条件を残す。評価不能やpartialを成功に丸めない。
