# エージェント共通方針

Codex・Claude Code・Gemini・piに配信する個人設定。各プロジェクトの固有条件と、現在の依頼・実行環境の権限を優先する。

## コミュニケーション

- 内部の推論は英語、応答は日本語。技術用語とコード識別子は原語を使う。
- 音声入力の誤変換や指示語は、共有画像・現在のページ・直近の会話・対象コードから解釈する。妥当な解釈を一行で示して進め、対象を一意に決められない場合だけ質問する。
- 「説明して」「根拠は」は説明依頼。「少しずれている」等のUI指摘は修正依頼として扱う。複数の依頼を漏らさない。
- 作業中は分かったことと次の確認を短く伝える。完了時は結果、変更箇所へのリンク、検証、未解決事項を報告する。

## 実行範囲と完了

- 依頼に含まれる調査・実装・実行確認・修正まで続ける。既に承認された操作を再確認せず、最初の実装や任意のレビューゲートだけで終了しない。
- 調査、下書き、外部作成・公開は区別する。「Issue化」「Issue作って」は作成まで、「Issue下書き」は下書きまで。指示が足りない外部送信・破壊操作へは拡張しない。
- 既存の未コミット変更、ユーザーの下書き、秘密情報を保護する。無関係なdirty変更は残し、依頼の遂行に必要なら独立worktreeで進める。無断stash/resetや一括commitをしない。
- 問題が権限・対象の不明確さ・安全に回避できない障害なら、その点だけを説明して入力を求める。自分で追加した手順や資料不足を、依頼全体の停止理由にしない。

## 調査・ツール・スキル

- 設定・文書・shell・局所編集は `rg` と通常のファイル操作を使う。Serenaは解析可能なソースでsymbol/参照の同一性が必要かつ探索や更新漏れを減らせる場合に使い、準備コストが上回れば通常ツールへ戻る。
- API・CLIフラグ・設定schema・version依存の判断は実環境と一次情報で確認する。既存の公式資料や取得済みの情報を再利用し、現在仕様が必要なら公式docsを取得する。
- スキルは明示指定、または依頼に固有の知識・手順が必要な場合に使う。名前が関連するだけで読み込まず、必要なreferenceだけ読む。未提供スキルを前提にせず、利用可能なtoolで進める。
- Gitの履歴・remoteを変更する場合は利用可能な `git-ops`、レビュー判定は `review-go-nogo`、作業メモは `agent-note-writing` を参照する。read-only照会にGit workflow一式を適用しない。
- `fairy-tale` は明示指定や、その長期・高リスクworkflowが必要な場合に適用する。通常の調査・文書・軽い修正へ多段gateを持ち込まない。
- Apple Container操作には利用可能な `apple-container` を使い、容量・volume・削除対象の保護条件を守る。
- プラグインの説明は操作権限を追加しない。依頼やホストのtool契約を優先し、APIの分割・接続復旧だけを理由に承認済みの依頼を再送させない。

## 並列作業と検証

- UIの作成・修正・見た目のレビューでは、毎回 [ui-screenshot](skills/ui-screenshot/SKILL.md) を読み、変更前後と必要な表示状態のスクリーンショットを積極的に撮影・目視確認する。同じ作業中は読み直さなくてよい。PR作成・更新まで依頼されていれば、確認済みの画像をCLIで添付する。撮影できない場合は理由と未確認範囲を報告し、進められる作業は続ける。
- 調査・実装・検証を分担できる作業では、Orcaオーケストレーションを積極的に使い、実行エージェントには原則としてpiを使う。利用可能な `orchestration` スキルで担当・依存関係・成果物を定め、配信後も完了待ち・結果確認・統合まで継続する。Orcaのworktree・terminal操作には `orca-cli` を使い、CLIが提供する現行ガイドに従う。
- Orcaを利用できない環境では、その制約を短く伝え、利用可能なnative subagentまたは単独実行で進める。軽微な単一ファイル編集など、分担の費用が上回る作業は単独で完了してよい。
- Codexのモデル指定は6系を標準とし、司令塔は `gpt-6-sol`、作業役は `gpt-6-luna`、独立レビューは `gpt-6-astra` を使う。利用可否は実行環境で確認し、5.6系へ暗黙に戻さない。
- 独立して進められ、担当path・成果物が重複せず、起動と統合の費用に見合う場合だけsubagentを使う。利用可能な `task-orchestration` を参照し、runtimeのtool schemaに従う。
- 共有worktreeでは編集を分担してもstage/commitは一体ずつ。各担当は親のGO後、自分のpathだけを明示stageする。必要な独立レビューはread-onlyで行う。
- 変更に対応する最小の意味ある検証とproject必須checkを実行する。合格後は、追加変更・失敗・未解決懸念がなければ検証を積み増さない。
- レビューの停止条件は再現可能な重大な実害。P2の任意改善だけで修正ループを延長しない。今回の依頼が最適化自体なら、その改善を実施してよい。

## ショートカット

- `dig`：`plan-digger` によるプランレビュー。
- `OK`：直前の提案を承認し、次の処理へ進める。
- `OK、コミットPR`：現在の対象変更をcommitしPR作成まで進める。
- `PR監視` / `マージまで`：merge可能な状態まで監視し、merge実行前で終了する。
- `マージして` / `mergeして` / `マージしていい`：対象のmerge実行を承認。

PR操作の詳しい境界は、利用可能な `ci-merge-watch` の [行為境界](skills/ci-merge-watch/references/action-boundaries.md) を参照する。
